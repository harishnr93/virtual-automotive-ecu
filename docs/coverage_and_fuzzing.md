# Code Coverage and Fuzzing

Two checks that complement the test suite:
- **coverage** measures which product code the tests actually execute
- **fuzzing** feeds millions of random inputs into every parser that reads data from outside the
  ECU, and checks invariants on each one

Both use only the existing toolchain (GCC gcov, Clang libFuzzer). No extra packages are needed.

```bash
./scripts/run_coverage.sh                       # build-coverage/, all tests -> docs/coverage_report.md (~6 min)
CXX=clang++ cmake -S . -B build-fuzz -DVECU_BUILD_FUZZERS=ON && cmake --build build-fuzz -j
ctest --test-dir build-fuzz -L fuzz              # 15 s per target (smoke run, also part of run_regression.sh)
setarch $(uname -m) -R ./build-fuzz/bin/fuzz_uds_server build-fuzz/tests/fuzz/corpus/uds_server \
    tests/fuzz/corpus/uds_server -max_total_time=600   # a longer campaign (ASLR off, see 2.3)
```

---

## 1. Code coverage

### 1.1 How it is measured
- GCC `--coverage -O0` build (`-DVECU_ENABLE_COVERAGE=ON`), then **all** tests: C++ unit and
  integration tests, Python unit tests, and the system tests that start real ECU processes. The
  counters of every process are merged by the gcov runtime.
- The watchdog's emergency exit ends the process with `std::_Exit`, which skips the normal exit
  that writes the counters. Coverage builds therefore flush them first (`__gcov_dump`); otherwise
  the safety paths that matter most would be missing from the report.
- `scripts/coverage_report.py` reads gcov's JSON output and reports product code only
  (`include/`, `src/`, `apps/`), per module and per file, plus every function that never ran.

### 1.2 Result (2026-10-28)
**87.0 % of lines (4301 / 4941) and 94.6 % of functions (695 / 735)**, with the full per-file table
in [coverage_report.md](coverage_report.md). By module, lines covered:

| Module | Lines |
|---|---|
| control | 94.2 % |
| faults | 93.6 % |
| core | 93.0 % |
| apps/cruise_ecu | 91.7 % |
| watchdog | 91.7 % |
| diagnostics | 87.7 % |
| firmware | 85.1 % |
| can | 79.4 % |

The 40 functions that never ran fall into explainable groups:
- **SocketCAN channel:** no `vcan0` on WSL2; the CI job `socketcan` is the place it can run.
- **`toString()` of error enums and error-message formatting:** reached only on error paths the
  tests do not trigger.
- **Usage texts, memory locking** (needs a permission this host does not grant), and two lambdas
  for configuration errors.

**What coverage does not say:** a line that ran was not necessarily *checked*; the assertions are
in the tests. Coverage shows where tests are missing, not that the code is correct.

### 1.3 Observed in the coverage run
One system test failed once in the coverage build: 3 confirmed DTCs instead of 2. The test passed
when re-run against the same binaries, and the instrumented ECU showed no deadline misses. The
cause could not be determined because the assertion printed only the count. It now prints the
confirmed DTCs, so a recurrence will show which fault qualified.

## 2. Fuzzing

### 2.1 Targets
Every parser that takes input from outside the ECU, with invariants checked on each input (a crash
or a broken invariant stops the fuzzer and saves the input):

| Target | Input | Invariants (beyond "no crash, no ASan/UBSan error") |
|---|---|---|
| `fuzz_isotp` | CAN frame sequences, flow control, sends | a reassembled message is 1–4095 bytes; every transmitted frame is valid |
| `fuzz_uds_server` | request sequences in all sessions, with download handler, routines, DIDs | a response fits the buffer; positive (SID + 0x40) or exactly a 3-byte NRC for the request's service; no active download outside the programming session |
| `fuzz_udp_wire` | software-bus datagrams + signal decoding | an accepted datagram is a valid frame and survives encode → decode unchanged |
| `fuzz_firmware` | image bytes and arbitrary boot-record content | the bootloader never reports a valid application whose image does not verify |
| `fuzz_nvm` | NVM file content | what loads is consistent and survives save → load unchanged |

The seeds (`tests/fuzz/corpus/`) are valid examples of each format, generated by
`tests/fuzz/make_seeds.py`, so the fuzzer starts deep inside the parsers. New inputs go to the build
tree, so the committed seeds never change.

### 2.2 Result (2026-10-28): 2 minutes per target, ASan + UBSan, ASLR off
| Target | Executions | Coverage points | Corpus | Peak RSS |
|---|---|---|---|---|
| `fuzz_udp_wire` | 93.5 M | 60 | 32 | 489 MB |
| `fuzz_isotp` | 8.7 M | 111 | 1619 | 428 MB |
| `fuzz_uds_server` | 4.5 M | 272 | 5119 | 455 MB |
| `fuzz_nvm` | 0.49 M | 117 | 25 | 364 MB |
| `fuzz_firmware` | 0.17 M | 122 | 54 | 326 MB |

**No crash, no sanitizer report, no invariant violation** in ~107 million executions. "Coverage
points" are libFuzzer's edge counters for the instrumented code reached.

Limits of this result:
- **`fuzz_firmware` is slow,** because every input builds a full 532 KB simulated flash. Its
  0.17 M executions explore far less than the other targets.
- **`fuzz_nvm` added no new inputs.** The NVM block is CRC-protected, so almost every mutation is
  rejected at the CRC check; the code behind it is reached only through the valid seed. A
  CRC-aware mutator would be the next step.
- Two minutes is a smoke-level campaign. Real projects fuzz for hours to days, continuously.

### 2.3 Finding: the sanitizer runtime crashed at start-up
The first parallel campaign lost a target to a segmentation fault: an empty log and no crash
input. It recurred in a *different* target on the next run, never under gdb, and never when the
target ran alone. gdb disables address-space randomisation, which was the clue. A direct test
confirmed it:

| 300 starts of `fuzz_udp_wire -runs=1` | Segfaults before the first input |
|---|---|
| with ASLR (default) | **81** |
| with ASLR disabled (`setarch -R`) | **0** |

It is a known incompatibility between the Clang 14 sanitizer runtime and the 32-bit mmap
randomisation of newer kernels (Linux ≥ 6.5, here WSL2 6.6); the project's code is never reached.
The TSan build already had this problem. The fuzz build now uses the same `setarch -R` test
launcher (`CMakeLists.txt`), and CI lowers `vm.mmap_rnd_bits`. Without that, the CTest smoke run
would fail at random about one time in four per target.

### 2.4 Limitations and next steps
- No structure-aware fuzzing (e.g. libprotobuf-mutator) and no CRC-fixing mutator, so the deep
  NVM and firmware paths are explored only around the seeds.
- The C++ code only. The Python DBC parser and tester are not fuzzed.
- No continuous fuzzing service; CI runs only the 15 s smoke run per target.
